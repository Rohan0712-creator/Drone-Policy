# Autonomous Drone Search & Rescue

A Python-based autonomous drone policy for finding and reporting survivors in a simulated collapsed-building environment while managing limited battery life.

## About the Project

This project was built as a search-and-rescue drone assignment.

The drone starts from a base at the corner of a **400 m × 400 m** search area. It has a limited battery and does not know beforehand how many survivors are present or exactly where they are.

The main challenge is to balance three things:

1. Search areas where survivors are more likely to be found.
2. Avoid making incorrect or duplicate survivor reports.
3. Make sure the drone has enough battery to return to the base.

The policy was implemented in Python and tested across **23 available scenarios**.

## What the Drone Does

The policy makes a decision before every drone action.

Depending on the current situation, it can:

* Fly to a new search location
* Change altitude and speed
* Hover to improve sensing
* Process survivor detections
* Declare a survivor and their triage level
* Stop searching and return to base
* Land safely when it reaches the base

The main policy is contained in:

```text
logic.py
```

## How the Policy Works

The policy is divided into a few smaller components instead of putting everything into one large decision-making function.

### Search and Coverage

The drone receives a prior probability map showing which areas are more likely to contain survivors.

I use this information to guide the search instead of treating every location equally.

The policy also keeps track of which areas have already been covered. This helps reduce unnecessary repeated searching.

### Survivor Tracking

A drone detection is not automatically treated as a confirmed survivor.

The same survivor can be detected several times, and the detected position can vary because of sensor noise. There can also be false detections.

The `SurvivorTracker` handles this by:

* Grouping nearby detections
* Keeping track of survivor candidates
* Updating their estimated position
* Counting repeated observations
* Recording when a candidate was seen
* Avoiding duplicate declarations

This makes the final survivor reports more reliable.

### Triage Handling

The simulator can provide one of three triage levels:

```text
critical
serious
minor
```

The `TriageManager` keeps track of the available triage information and helps decide which triage value should be used when a survivor is declared.

The scoring system also gives different importance to the three categories, with critical survivors having the highest weight.

### Battery Management

Battery management is one of the most important parts of the policy.

The drone should not continue searching until the battery is almost empty because it still needs enough energy to get back to the base.

The `BatteryManager` estimates the energy required to return based on:

* Current distance from the base
* Estimated flight time
* Recent power consumption
* A safety factor
* A fixed reserve

Power consumption is smoothed using an **Exponential Moving Average (EMA)** so that one unusual measurement does not immediately cause an unstable decision.

If the remaining battery is not enough for a safe return, the policy switches to return mode.

### Flight Controller

The `FlightController` is responsible for making sure the actions generated by the policy stay within the simulator's allowed limits.

For example, it keeps:

* Position inside the search area
* Altitude between the allowed minimum and maximum
* Speed within the allowed range
* Hover duration within the valid range
* Triage values valid

This keeps the action-generation part separate from the main decision-making logic.

## Overall Architecture

```text
                     Policy
                       |
          +------------+------------+
          |            |            |
          v            v            v
   SurvivorTracker  TriageManager  BatteryManager
          |            |            |
          +------------+------------+
                       |
                       v
                FlightController
                       |
                       v
                 Drone Action
```

The idea is simple: the `Policy` decides what should happen, while the supporting classes handle tracking, triage, battery safety, and valid action construction.

## Running the Project

The simulator requires **Python 3.10**.

Install the dependencies:

```bash
py -3.10 -m pip install -r requirements.txt
```

Run the calibration scenarios:

```bash
py -3.10 run_local.py logic.py --scenarios calibration
```

Run one specific scenario:

```bash
py -3.10 run_local.py logic.py --seed 1007 --verbose
```

Run all available scenarios:

```bash
py -3.10 run_local.py logic.py --scenarios all
```

Create a flight visualization:

```bash
py -3.10 visualize.py logic.py --seed 9001 --out ep.png
```

## What I Learned

Working on this project involved more than just writing a path for the drone to follow.

The main things I worked with were:

* Object-oriented Python
* Autonomous decision making
* Probability-based search
* Noisy sensor data
* Spatial clustering and tracking
* Triage-based prioritization
* Battery-aware planning
* Safe return-to-base logic
* Simulation and scenario-based testing

One of the main design decisions was to avoid treating every detection as a confirmed survivor. Instead, detections are tracked over time and combined when they appear to belong to the same location.

Another important part was battery management. A drone that finds survivors but cannot return safely is not a successful search policy, so the return decision is treated as part of the planning process rather than something handled at the very end.

## Final Result

The final policy successfully completed all **23 tested scenarios**, with:

* **+0.4103 mean score**
* **23/23 successful landings**
* **0 crashes**
* **0 timeouts**
* **0.13 false declarations per scenario**
* **22.5 ms maximum action-decision time**

The project gave me practical experience in designing a small autonomous system where search efficiency, noisy observations, decision making, and resource constraints all have to work together.
